Enterprise Text-to-SQL — fine-tuning, measured

A QLoRA-fine-tuned Qwen3-8B turns business questions into PostgreSQL. Fine-tuning took strict execution accuracy from 43.71 % to 68.43 %, and 70.86 % with a self-correction loop — measured on 453 held-out questions by executing every query against a real database, never by string similarity.

This is the project's second iteration. The first scored 52.10 %, and analysing its failures showed most of that gain was the model learning which columns the benchmark wanted. Scoring both pipelines on this identical test set: strict accuracy 40.18 % → 70.86 %, while genuinely wrong row sets went 85 → 84. The headline moved 30 points; the SQL barely improved. That is the honest read, and it is only visible because the harness separates the two.

The hard tier — multi-table joins and subqueries — is where reasoning genuinely improved. medium did not move at all: a failure analysis traces 24 of its 25 remaining misses to one template whose gold renders months as EXTRACT(MONTH) while the model writes DATE_TRUNC — same 12 rows, different representation.

Two results that did not go as expected

Schema retrieval made things worse — twice

Showing only the retrieved tables cost the base model 1.55 points and the fine-tuned model 9.27. The adapter only ever saw full-schema prompts, so subsets are out of distribution for it — and the damage lands on hard (−20.8) and enterprise (−13.1), the tiers that need joins. Drop a table a join needs and the model invents one: hallucination nearly doubles.

With 12 tables the whole schema is 5,455 characters. Retrieval solves a problem this database does not have.

Self-correction: two rates, not one

repair success — now executes11 / 1957.9 %
repair correctness — right rows5 / 1926.3 %

Six of the eleven "successes" turned a crash into a confident wrong answer. One rate would have claimed 57.9 % and hidden that.

Repair works when the error names the fix (column "method" does not exist → rename to payment_method) and fails when it names only the symptom (ambiguous column reference).

        → success → rows
        → failure → repair    the database's own error fed back, retried once

How correctness is judged

By execution, never string similarity. Every prediction runs against PostgreSQL and its result set is fingerprinted. These are different strings and both count as correct:

SELECT COUNT(*)           FROM customers WHERE country = 'India';
SELECT COUNT(customer_id) FROM customers WHERE country = 'India';

Order is compared only where the gold query has an ORDER BY. A second, projection-tolerant metric wraps the prediction in a subquery and asks for the gold columns — that is what separates "wrong columns" from "wrong rows", and it is the whole reason the 159 → 0 finding above is visible at all.

Why completion-only loss is the detail that matters. Each example is ~1,490 prompt tokens and ~46 completion tokens, and the prompt is ~97 % schema, byte-identical across all 2,133 examples. Training on the full sequence sends ~97 % of the gradient into memorising a schema the model is handed at inference — and the loss curve looks excellent throughout, because predicting a constant is easy.

Limitations

  • Schema-specific. It learned this database's conventions — that is most of the measured gain.
  • Roughly half its answers are still wrong under strict scoring. Classifying all 217 failures: 118 return the right rows under a different column set (the question never said which columns), 91 are real logic errors — mostly business definitions the prompt never states — and 8 are detectable errors. Row-level accuracy is 78 %; the strict number stays the headline.
  • Test questions are template-generated, from the same generator as training. Real user phrasing — abbreviations, typos, ambiguity — is untested. The biggest caveat on the headline number.
  • One epoch, one seed, one run. No variance estimate.
  • Silent wrong answers are the real risk. SQL that runs and returns the wrong rows is indistinguishable from a correct answer without a gold reference — and repair cannot help, because there is no error to feed back.
