## Change 1 — thresholds derived from the data

Revision 1 drew numeric thresholds from hand-written lists chosen without
looking at the data. Two failure modes followed.

**Empty results (81 rejected examples).** The minimum credit limit is 5,000, so
"credit limit below 1,000" matched nothing. No department averages above
100,000, so that question was unanswerable too.

**Vacuous predicates (195 affected examples).** The minimum salary exceeds
50,000, so `salary > 40000` and `salary > 50000` returned identical rows. A
model ignoring the threshold entirely still scored correct.

Both have the same root cause: **the threshold was not drawn from the
distribution it is compared against**. The fix is a pool per column, built from
interior deciles:

```sql
WITH src AS (SELECT salary AS x FROM employees),
     bounds AS (SELECT MIN(x) lo, MAX(x) hi FROM src),
     q AS (SELECT unnest(percentile_cont(ARRAY[0.1,...,0.9])
                         WITHIN GROUP (ORDER BY x)) AS v FROM src)
SELECT DISTINCT ROUND(v) FROM q, bounds
WHERE ROUND(v) > bounds.lo AND ROUND(v) < bounds.hi
```

Excluding the bounds is the whole mechanism: a value strictly inside the range
always splits the rows into two non-empty parts, so the predicate always does
real work. Counts per group (line items per order, warehouses per product) use
every distinct value in `[min, max)` instead, since deciles would collapse onto
the same few integers.

23 derived pools replaced 10 arbitrary ones. A slot is now named for the column
it belongs to, so two templates comparing against different distributions can
never share a pool — the mistake that produced "average salary above 100000".

| Was | Now |
|---|---|
| `{salary}` for both raw and averaged salary | `{employee_salary}`, `{dept_avg_salary}` |
| `{price}` for both unit and category-average price | `{product_price}`, `{category_avg_price}` |
| `{amount}` for order totals, credit limits, payments | `{order_total}`, `{customer_credit_limit}`, `{payment_amount}` |
| `{qty}` for stock, sales volume, payment counts | `{inventory_qty}`, `{product_total_qty}`, `{product_total_stock}`, `{payment_method_uses}` |
| `{n}` for LIMIT *and* customer-count thresholds | `{n}` (LIMIT only), `{country_customer_count}` |

Three second-order cases surfaced during revalidation and were fixed the same
way rather than tolerated:

- `{year}` came from order dates but was used to filter *signup* and *hire*
  years with `>`. Since both extend to the latest year, "signed up after 2026"
  matched nothing. Added `{signup_year}` and `{hire_year}`, both excluding
  their maximum.
- `{warehouse_city}` included the two cross-dock warehouses that hold no stock,
  so "products stored in Austin" was correctly empty. It now draws only from
  warehouses that have inventory.
- `{n}` was used as a LIMIT over warehouses, but only 13 hold stock — so "top
  50" and "top 100" both returned all 13, a vacuous limit. Added
  `{warehouse_limit}`, bounded by the number of stocked warehouses.

## Change 2 — realistic unreferenced entities

Revision 1 distributed foreign keys uniformly, so every product was ordered,
every warehouse stocked, every supplier supplying. Six templates asking "which
X has no Y?" correctly returned nothing and were eliminated, taking the

## Change 3 — time-relative questions anchored to `DATA_AS_OF`

Revision 2 flagged that some gold queries compared against `NOW()`, so their
result sets drift as the clock advances. That is now fixed.

### Why it mattered

The project's central claim is measured by comparing a base model (Phase 5)
against a fine-tuned model (Phase 10) on the same benchmark. Those runs are
weeks apart. With `NOW()`, the gold answer moves between them, so the two models
would be graded against **different correct answers** — while still producing
plausible-looking accuracy numbers. A silent failure of exactly the kind
execution-based evaluation is supposed to prevent.

Measured against the live database, only 9 days after `DATA_AS_OF`:

| Template | Anchored | With `NOW()` | Drift | Question |
|---|---:|---:|---:|---|
| `x14` | 1,136 | 1,160 | +24 | customers who have not ordered in N months |
| `x29` | 1,315 | 1,335 | +20 | orders pending more than N days |
| `x30` | 178 | 154 | −24 | inactive customers ordering within N months |
| `x17` | 2 | 2 | 0 | this year versus last year |

Three of four gold answers had already moved after nine days. `x17` shows no
drift today only because the year has not turned; `DATE_TRUNC('year', NOW())`
jumps on 1 January and the query then covers a different two-year window.

### How it is anchored

`DATA_AS_OF` is defined once in [`src/constants.py`](../../src/constants.py):

```python
DATA_AS_OF: datetime = datetime(2026, 8, 1, 0, 0, 0, tzinfo=timezone.utc)
DATA_AS_OF_SQL: str = f"TIMESTAMPTZ '{DATA_AS_OF.isoformat(sep=' ')}'"
```

The SQL literal is derived from the Python value, so the two cannot drift apart.
Every consumer imports this one definition:

| Consumer | Use |
|---|---|
| `scripts/generate_data.py` | clamps payment, shipment and delivery timestamps |
| `dataset/generation/templates.py` | resolves `{as_of}` into gold SQL |
| `dataset/generation/value_pools.py` | measures elapsed-time threshold pools |
| `scripts/validate_dataset.py` | executes gold SQL; records the anchor in the report |
| Phase 4+ evaluation | inherits it — the literal is baked into the stored SQL |

Templates write `{as_of}`, which the `T()` constructor replaces with the literal
**at definition time**, before slot filling. So it never becomes a fillable slot
needing a value pool, and never has to appear in the question text — which is
what keeps the questions unchanged.

The threshold pools moved to the same anchor. Measuring elapsed time from
`NOW()` while the queries filter on `DATA_AS_OF` would compute thresholds
against a different reference point than the one they are applied to, drifting
further apart every day.

### Semantics are unchanged

Only the reference point moved. Each question means what it always meant,
relative to the instant the dataset is "current":

| Template | Before | After |
|---|---|---|
| `x14` | `MAX(order_date) < NOW() - INTERVAL 'N months'` | `... < {as_of} - INTERVAL 'N months'` |
| `x17` | `order_date >= DATE_TRUNC('year', NOW()) - INTERVAL '1 year'` | `... DATE_TRUNC('year', {as_of}) ...` |
| `x29` | `order_date < NOW() - INTERVAL 'N days'` | `... < {as_of} - INTERVAL 'N days'` |
| `x30` | `order_date > NOW() - INTERVAL 'N months'` | `... > {as_of} - INTERVAL 'N months'` |

No question text was edited.

### Verification

`x17` was **not** in the original list of three. It was found by grepping the
template library for every time-relative construct, and carries the same defect,
so it was fixed too — leaving it would have meant reporting the issue as fixed
while one template still drifted.

| Check | Result |
|---|---:|
| Examples anchored to `DATA_AS_OF` | 78 |
| Examples still using `NOW()` | **0** ✅ |
| Execution failures | **0** ✅ |
| Leakage | **0** ✅ |
| Templates retained | **174 / 174** ✅ |
| New result-set collisions | **0** — identical set to revision 2 ✅ |

The validator now counts `NOW()` occurrences on every run and prints the anchor,
so a reintroduced drift shows up immediately rather than being discovered months
later in a corrupted comparison. `data_as_of` is recorded in
`validation_report.json` so a future evaluation can confirm it is comparing
against gold results produced under the same anchor.

The four anchored templates sit in three different splits — `x14` test, `x17`
and `x29` validation, `x30` train — so the fix is exercised on both sides of the
train/test line.

### Why not a random row split

The three phrasings of one template with one slot value are near-identical. A
random split would scatter them across train and test, letting a model memorise
a pattern in training and reproduce it at test time. The reported accuracy would
measure recall, not generalisation.

Splitting on template means test questions use **query patterns the model has
never seen**.

Train holds fewer templates than the other splits despite holding 70 % of the
examples. Groups are assigned largest-first, so a few high-yield templates —
those whose slots multiply out to many combinations — fill train's quota, while
smaller templates spread across validation and test. Difficulty stratification
still holds within each split.

### Equivalence groups

Templates emitting byte-identical SQL are merged and assigned together, since
two templates producing the same query are one query wearing two ids.
**0 groups needed merging**: all 174 templates produce distinct SQL.

## Remaining known limitations

### Four result-set collisions (24 examples, 0.8 %)

Down from 14 collisions and 195 examples. **None is a vacuous predicate** — every
threshold now does real work. These are genuinely different questions that
happen to share an answer:

| Templates | Cause |
|---|---|
| `e01` / `e02` | Singapore is both a country and a city, so "customers located in Singapore" has one answer under either reading |
| `e17` / `e18` (×2) | the 90th percentile of 500 salaries *is* the top 50 — arithmetic, not a bug |
| `m01` | `COUNT(*)` for Germany and Japan coincidentally returns the same number |

Two distinct questions sharing an answer is normal and not removable in general.
Left as-is and recorded.

*(The time-drift limitation reported in revision 2 is now fixed — see Change 3.)*

## Reproducibility

Deterministic in both senses that matter. Regenerating and revalidating produces
byte-identical output, and — since revision 3 — that remains true **when run on
a different date**, which is what makes a Phase 5 baseline comparable to a
Phase 10 evaluation.
`validated.jsonl` carries each example's execution metadata — row count, column
names, latency, and an order-insensitive result fingerprint — so Phase 4 can
score execution accuracy by comparing fingerprints without re-running the gold
queries.
